# paip vs Palantir AIP 流水线对比分析

- 日期：2026-08-07
- 目的：理解 Palantir 最新 AIP 流水线各环节（做什么/为什么/结果），逐环节对比我们的 paip 设计，定位差距根因，给出修改建议作为迭代依据
- 资料基线：`palantir-like-workflow/README.md`（2026-08-05 调研，13 个一手来源）+ Palantir 官方文档抓取（2026-08-07，research 子代理）；未验证项均已标注
- 关联：`docs/2026-08-07-paip-capability-test-report.md`（能力测试发现的 P1-P14，本文档的差距分析与其互相印证）

## 一、Palantir AIP 流水线环节总览（做什么 / 为什么 / 结果）

| # | 环节 | 做什么 | 为什么（官方设计理由） | 结果 |
|---|---|---|---|---|
| 1 | 数据接入与 Schema 推断（Indexing / Hydration / Infer schema） | 联邦直连数据源（不复制），自动推断 schema，映射进 Ontology | without duplicating the underlying data——避免第二真相源；schema 是事实 | 对象/属性/链接雏形 + 可建模数据 |
| 2 | 转换逻辑生成（Pipeline Builder） | 自然语言→自动生成转换代码（Generate）；可插入 LLM 节点；Transform Assist 辅助正则 | 逻辑作为确定性工具（可审计可重放）；严格输出检查防下游破坏；独立管道逻辑可换执行引擎（Spark/Flink） | 可执行的管道 + 物化 dataset / 对象类型 |
| 3 | 语义建模（Ontology Manager） | 选数据源→自动映射每列为属性→自动推断 ID/类型→一键生成标准动作 | 建模是解释不是事实；向导降低人工成本；动作让模型可被运营系统消费 | 对象类型 + 动作类型（写回能力） |
| 4 | 实体消解（Entity Resolution） | AI 跨源链接记录去重 | false positive 比 false negative 危险；去重是建模中最脏最累环节 | 可靠去重后的数据地基 |
| 5 | 语义检索与接地（Semantic Search / OAG） | embedding 向量关联 Ontology 对象；LLM 生成以语义模型接地 | 对抗朴素 RAG 幻觉；搜索驱动的运营工作流 | 可语义检索的运营层 |
| 6 | LLM 函数与动作层（AIP Logic / actions） | 无代码 LLM 函数；函数可编辑 Ontology，**可自动应用或暂存人工审核**；最小权限 | LLM 非确定性需要人审闸门；最小权限安全 | 可编排的 AI 动作 + 治理闸门 |
| 7 | 评估（AIP Evals） | 测试用例+目标函数+评估函数+指标，跨版本/跨模型对比 | 专门应对 LLM 非确定性，建立投产信心 | 评估报告（可写回 dataset/dashboard） |
| 8 | 治理层 | human review checkpoints、动作审计、最小权限、模型可替换 | AI 出提案人审查；动作可审计；主权 AI（模型自托管） | 可信的 AI 决策闭环 |
| 9 | 消费端 | Workshop / OSDK / Object Explorer / Bootcamp | 模型要被人用起来才有价值；几天交付真实工作流 | 运营工作流 + 快速交付方法论 |

## 二、逐环节对比：Palantir vs paip

### 环节 1：数据接入与 Schema 推断

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | 联邦直连（BigQuery/Snowflake/S3），Infer schema，Indexing 物化 | `paip-source`：sources/<id>.json 联邦引用（路径）+ `schema-infer.js` 推断 | ✅ 设计对齐（联邦引用原则一致） |
| 为什么 | 不复制=无第二真相源 | 同 | — |
| 结果 | 对象雏形 + 可建模数据 | schemas/*.schema.json + 注册表 | ✅ |

**差异点**：
- Palantir 的 Indexing 是**持续物化**（数据源变更→对象存储同步）；我们是**一次性读取**（exec 时读文件，无变更检测/增量）。→ 对单机演示足够，但"数据源更新后管道自动感知"能力缺失。
- schema-infer 对脏日期/金额推断为 `mixed` 无上下文（P5，已在能力测试记录）；Palantir Infer schema 面向"无 schema 数据入口"场景，配合向导后续处理。

### 环节 2：转换逻辑生成（Pipeline Builder）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | Generate（NL→转换代码）+ Use LLM node + Transform Assist + 严格输出检查 + 引擎可替换 | `paip-model`：LLM 生成 9 种确定性规则 JSON + `exec.js` 纯 JS 行级执行 | ⚠️ 核心对齐但缺 3 项 |
| 为什么 | 逻辑确定性 + 防下游破坏 + 引擎解耦 | 同（确定性原则是设计核心） | ✅ |
| 结果 | 可执行管道 + 物化 dataset/对象类型 | output/<id>.csv 物化 | ⚠️ 无对象类型产出 |

**差距与根因**：
1. **Use LLM node 缺失（设计取舍）**：Palantir 允许管道内插入 LLM 节点（清洗/抽取/分类），用 Evals+审计兜底非确定性；我们**一刀切禁止**（9 种规则全是确定性函数）。根因：确定性优先哲学 + 无评估兜底设施。**结果**：语义类任务（分类、抽取实体、情感判断）无法进管道——这是"AI 原生流水线"的核心能力之一，我们只做了"AI 生成规则"，没做"AI 执行任务"。
2. **严格输出检查缺失（P14 相关）**：Palantir 构建时检查输出 schema，不通过则阻止构建防下游破坏；我们 validate 只查规则输入（列存在/参数齐全），**不查规则对输出列结构的影响**（如 cast 把列变空、split 新增列后下游规则引用）。根因：validate 设计时聚焦"规则合法性"未扩展"下游影响"。结果：链式规则中后规则引用前规则新列时，如果前规则改了列结构，错误只能执行时暴露。
3. **引擎可替换**：Palantir 管道逻辑与执行引擎解耦（Spark/Flink 可换）；我们 spec §2 已声明"JS 参考实现 + 未来后端适配器"，接口留好但未实现抽象层（exec 直接读规则 JSON 执行）。→ 设计到位、实现未做。

### 环节 3：语义建模（Ontology Manager）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | 向导：自动映射列→属性、自动推断 ID/类型、**一键生成标准动作** | `paip-infer`：LLM 从 schema 生成对象/属性/链接（JSON 到 staging） | ⚠️ 部分对齐 |
| 结果 | 对象类型 + **动作类型** | objects/links JSON | ⚠️ 无动作概念 |

**差距**：
1. **无"动作"概念（结构缺口）**：Palantir Ontology 是"语义+动能"两层——对象描述世界，**动作改变世界**（写回运营系统、可审计）。我们只有物化 CSV（output/），无动作类型定义。根因：范围裁剪（"决策写回"被认为超出演示范围）。结果：流水线是"单向读-算-写文件"，不是"闭环治理"。
2. 自动映射列→属性：我们由 LLM 做（prompt 要求每列映射为属性）——能力等价但**无确定性兜底**（LLM 漏列时无自动检查）；validate 检查对象有 properties 但不检查"属性是否覆盖 backingSource 全部列"。→ 可加"列覆盖检查"。

### 环节 4：实体消解（Entity Resolution）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | AI 跨源链接去重（产品级：规则配置+概率匹配+人工确认） | `paip-entity`：LLM 判定匹配对（≥0.9 置信度）+ `exec.js` 键映射替换 | ⚠️ 简化版 |
| 为什么 | 去重是最脏最累环节；false positive 危险 | 同（宁缺毋滥原则已写入 skill） | ✅ |

**差距**：我们靠 LLM 直接产出"精确键值对"（声明式），缺 Palantir 的**候选生成**（阻塞/相似度函数）+ **审查工作台**（匹配结果可视化确认）。根因：演示规模下 LLM 直出足够；规模大后 LLM 直出不可行（全量两两比较）。→ 中期增强方向。

### 环节 5：语义检索与接地（Semantic Search / OAG）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | embedding 关联 Ontology 对象；LLM 生成以语义模型接地防幻觉 | **无**（spec v2.2 OAG-lite 未来项） | ❌ 完全缺失 |

**差距根因**：v2 spec 明确"OAG 核心=语义模型+查询+来源引用，embedding 是增强不是核心"并推迟到 v2.2。**但对比后应修正判断**：我们的 LLM 建模输入是 schema JSON（已接地），而**消费端**（业务问答、基于 Ontology 的生成）完全没有——OAG 在 Palantir 是"生成层的地基"，不只是增强。**结果**：流水线产出（objects.json + output/）没有"被语义消费"的路径。

### 环节 6：LLM 函数与动作层（AIP Logic）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | 无代码 LLM 函数；函数编辑 Ontology 可**暂存人工审核** | 无对应（paip-review 的 staging 机制最接近） | ❌ 无函数/动作概念 |
| 为什么 | 非确定性需要人审闸门；最小权限 | — | — |

**差距**：我们的 staging→review 机制**精神一致**（AI 产物暂存待审）但作用对象不同——Palantir 审核的是"动作"（会改变 Ontology 的编辑），我们审核的是"声明"（规则/模型 JSON）。审核"声明"更安全（无副作用），但意味着**没有 AI 直接作用于数据的路径**（一切都要人先批准规则）。→ 设计取舍合理（零副作用铁律），但缺"暂存可审核的动作"概念（如 exec 产物暂存待审而非直接写 output/）。

### 环节 7：评估（AIP Evals）

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | 测试用例+评估函数+指标，跨模型/版本对比 | **无**（spec v2.1 evals-lite 未来项） | ❌ 完全缺失 |
| 为什么 | 专门应对 LLM 非确定性 | — | — |

**差距根因**：v2.1 被定义为"后续阶段"。**但对比后应提前**：能力测试已证明我们 LLM 生成的规则**会错**（P14 日期规则月日颠倒、P4 金额规则覆盖不全）——没有评估设施，"AI 生成规则质量"只能靠 validate 的格式检查 + 人工审查，**无量化反馈**（清洗后脏值率多少？规则有没有副作用？）。AIP Evals 给 Palantir 的正是这个量化闭环。

### 环节 8：治理层

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | human review + 动作审计 + 最小权限 + 模型可替换 | `paip-review` + `audit.js` | ⚠️ 部分对齐 |
| 结果 | 可信决策闭环 | audit.jsonl + approved/ 不可变 | ✅ |

**差距**：
- 审计：我们逐动作审计 ✓（P13 发现 state.sources 双轨制小问题）。
- 最小权限：无概念（单机单用户，可接受）。
- **模型可替换：无**——config.json 有 llm 段（preferredModel/fallbackModel）但引擎不消费；Palantir 的"模型可替换+跨模型评估"（Evals 跨模型对比）我们没有。→ 与环节 7 同根因。

### 环节 9：消费端

| | Palantir | paip | 差距 |
|---|---|---|---|
| 做什么 | Workshop/OSDK/Object Explorer 消费 Ontology；Bootcamp 几天交付 | **无消费端**；demo-data 承担演示角色 | ❌ 无消费路径 |
| 结果 | 运营工作流 | output/ CSV（无消费示例） | ⚠️ |

**差距**：流水线产出物（objects/links/transforms/merges/output/）没有"怎么用"的定义——没有查询示例、没有报表示例、没有应用接入。根因：范围裁剪。结果：演示止步于"跑通"，未展示"跑通了有什么用"（优化故事的 6 类病症定位在 README 里只有文字指南，无实际查询工具）。

## 三、差距根因总结

| 根因 | 表现 |
|---|---|
| **范围裁剪（YAGNI 决策）** | Evals/OAG/LLM 节点/动作层/消费端 全部被推迟到 v2.1/v2.2/未来——但对比显示其中 Evals 与 LLM 节点是"AI 原生流水线"的**核心闭环**而非增强 |
| **确定性优先哲学的一刀切** | 为保住"可重放"禁止 LLM 节点；Palantir 用 Evals+审计+人审闸门**管理**非确定性而非禁止它——我们的选择更安全但丢掉了 AI 执行能力 |
| **校验只查输入不查输出** | validate 检查规则合法性与列存在，不检查输出列结构变化的下游影响（Palantir 严格输出检查）——P14 值篡改能漏过就是因此 |
| **单机零依赖的规模设定** | 无索引/无持续物化/无候选生成——演示场景够用，规模语义缺失 |
| **信息差** | 设计时未充分对照官方机制（严格输出检查、Logic 暂存审核、Evals 定位）——本次对比补齐 |

## 四、修改建议（按优先级）

### 近期（下一迭代，直接可做）

1. **规则效果评估（evals-lite，对齐 AIP Evals 最小版）**
   - `bin/eval.js <项目> <规则id>`：执行单条规则前后对比——输出脏值残留率、空值率、行数变化、样本前后对照
   - 接入 paip-model skill（生成规则后必须跑 eval 看效果再进 staging）与 paip-review（审查时展示评估数据）
   - 修复 P4（金额规则覆盖不全）与 P14（值篡改）的可量化检测：eval 能发现"清洗后仍残留"与"值语义改变"
2. **validate 下游影响检查（对齐严格输出检查）**
   - 校验规则对输出列结构的影响：cast 失败率预检（抽样）、规则引用链上"前规则输出列"存在性（P14 的链式值验证自动化）
3. **日期/金额清洗标准模式入库**（P10/P4）：skill 或 docs 提供"三格式日期→ISO"与"多格式金额→数字"的标准规则模板

### 中期

4. **LLM 节点（对齐 Use LLM node，带治理）**
   - 新增规则类型 `llm_transform`（输入列、输出列、任务描述、模型引用）；执行时调用 config 的 llm 通道；审计记录输入样本/输出/耗时
   - 配套 evals-lite 强制评估 + 人工审查（对齐 Palantir"暂存人工审核+最小权限"）
5. **OAG-lite（对齐 OAG，修正 v2.2 定位）**
   - 基于 objects.json + output/ 的"语义问答"入口：LLM 生成时注入语义模型（对象/属性/链接）作为接地上下文，输出要求引用来源
6. **动作/写回语义（对齐 actions 最小版）**
   - 定义"物化即动作"：output/<id>.csv 写回审计 + 明确的消费契约（查询示例/报表示例），让优化故事有实际查询工具支撑

### 长期

7. **Entity Resolution 增强**：候选生成（同源阻塞键）+ 相似度阈值 + 审查工作台（合并建议可视化确认）
8. **引擎适配层落地**：exec 的"规则 IR → 后端"抽象（SQLite 后端作第二个实现，JS 作差分基准），兑现 spec §2 的接口承诺
9. **模型可替换闭环**：config.llm 被引擎消费 + 跨模型评估（同一规则/函数在两个模型上的结果对比）

## 五、结论

- **对齐良好的环节**：数据接入（联邦引用）、转换确定性化、人工审查+审计、宁缺毋滥消解原则——设计哲学与 Palantir 一致
- **核心差距**：评估闭环（Evals）、LLM 执行节点、语义接地（OAG）、动作/消费端——都是"AI 原生流水线"的**闭环组成部分**，我们因范围裁剪推迟了它们，导致流水线"能跑但不会自我改进、不会执行 AI 任务、产出无人消费"
- **根因不是能力不足而是定位偏差**：把"评估/LLM 节点"当增强推迟，实际它们是闭环必需件；本次对比建议将其提前，与能力测试的 P4/P14（规则质量无量化反馈）互相印证

## 六、验证与局限

- Palantir 侧结论均锚定本地调研报告（一手来源清单见其 §7）与 research 官方文档抓取；**未验证项**：OAG 官方正文、Entity Resolution 官方独立页面（疑似 404，官方机制为 Indexing/Object edits）、release notes 新功能
- 我们侧结论基于 `spec/2026-08-05-paip-engineering-design.md`、8 个 SKILL.md、引擎源码与能力测试报告（P1-P14）
- 建议的可行性论证（如 evals-lite 的具体指标）应在实现前用 confirm-by-experiment 验证
