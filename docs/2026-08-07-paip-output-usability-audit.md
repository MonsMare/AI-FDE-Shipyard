# paip 交付结果可用性审计（企业优化视角）

- 日期：2026-08-07
- 工具：`palantir-aip-workflow/demo-data/verify/output-audit.js`（在项目副本上执行 exec 全量后检查产物）
- 对象：`demo-data/company-group`（Meridian 控股集团，64 表 12.86MB，16 转换 + 20 合并）
- 触发原因：检验 paip 流水线交付结果能否直接用于企业优化分析

## 一、总体结论

**部分可用，实体消解层不可直接消费。**

| 层 | 判定 | 依据 |
|---|---|---|
| 数据清洗/规范化层（16 个转换产物） | ✅ **可直接消费** | 日期 0 残留、金额 0 空值、trim 0 残留、行数守恒 15/15 零丢失、mapping 一致性 20/20 |
| 业务病症信号（6 类） | ⚠️ **5/6 保留，1/6 被抹除** | 库存积压 996 行、churn 前兆 850/865 订阅（98%）、供应链延迟 22 家、员工流失 400 行、缺陷 2000 行可检出；**负数量信号（831 行）被 qty_abs 转正抹除** |
| 实体消解层（20 个合并产物） | 🔴 **4 类关联破坏，不可直接用于跨系统客户分析** | 见问题 A1-A4 |

## 二、各检查域结果

### A. 产物完整性 ✅
- 56/56 产物齐全（16 转换 + 20 合并 + 20 mapping），无缺失/多余，文件名与规则 id 一一对应。

### B. 数据质量 ✅（清洗层优秀）
- 日期链式清洗后：`date` 列非 ISO 残留 **0**（12000 行全部 `YYYY-MM-DD`）。
- 金额链式清洗后：`base_salary` cast 空值 **0**、非正值 **0**（8000 行全部合法正数）。
- trim/lower/map/regex 全部生效：`company_name` 首尾空白残留 **0**。
- 行数守恒：15 条非 filter 转换全部 `lost: 0`（无意外丢行）。

### C. 关联一致性 🔴（合并产物 4 类问题）

**A1. 合并产物主键重复（16/16 产物）**
- 每个客户合并产物均出现主键重复：`merge_cust_rs_1.csv` 中 `CUST-1` 出现 **2 行**（左表原行 + saas 行改键后追加）。
- 根因：`applyMerge` 将右表匹配行改键后**追加**（union 语义），不合并/覆盖左表行。
- 影响：下游按 `customer_id` join 该产物必产生 fan-out（一对多）；主键约束被破坏。

**A2. 实体消解后事实表外键 100% 失配（saas 侧）**
- `subscriptions.customer_id` 共 2604 个唯一引用（`SC-*`），在全部 16 个客户合并产物的键集合中 **0 命中**。
- 根因：合并把 `SC-1` 等键物理改写为 `CUST-1`/`MC-1`（左表键），但引用 `SC-*` 的事实表（subscriptions/usage_metrics/invoices_saas）**不联动**。
- 影响：订阅→客户 join 全断，"客户 360 视图"无法构建；这是实体消解物理化的固有代价（Palantir 用 Ontology 逻辑层避免物理改写）。
- mfg 侧（shipments_mfg 引用 `MC-*`）1100/1100 命中，是因为 `merge_cust_ms_*` 产物含完整 mfg 客户表（`MC-*` 未全部改键）——**偶然保全，非设计保证**：`MC-111..114` 已被 `rm_*` 改键为 `CUST-111..114`，引用它们的行在"retail 视角"产物中同样失配。

**A3. 同一实体被分裂进两个 canonical 实体（声明矛盾）**
- `SC-1`（saas 客户）同时被 `merge_cust_rs_1`（→ `CUST-1`）与 `merge_cust_ms_1`（→ `MC-1`）引用：实测其 email 行**同时出现**在两个合并产物中（`split: true`）。
- 根因：rules.js 的声明中 `SC-1..4` 被两组 merge 重复引用（retail↔saas 与 mfg↔saas），且右侧表在多次合并间从不更新（`tables.set` 只写回左表）。
- 影响：同一客户被计入两个实体，跨系统客户计数/去重失真。

**A4. 实体消解覆盖率仅 8%**
- 设计埋点 194 对重复客户，仅声明 16 对（coverage 8%）。
- 影响：合并产物远非"客户主数据全集"——剩余 178 对重复客户在产物中仍是重复记录；下游若把合并产物当主数据用，会得到**不完整的去重视图**（且与原始三表的关系无定义）。

### D. 病症可见性 ⚠️

| 病症 | 信号 | 检出现状 |
|---|---|---|
| 库存积压（stock > 400） | 996 行 | ✅ 可检出 |
| churn 前兆（will_churn 订阅后半程骤降） | 850/865 订阅（98%） | ✅ 可检出 |
| 供应链延迟（lead_time > 30 天） | 22 家供应商 | ✅ 可检出 |
| 员工流失（employee_exits） | 400 行 | ✅ 可检出 |
| 质量缺陷（defects） | 2000 行 | ✅ 可检出 |
| **负数量/退款差错** | 原始 **831 行**负数量 → qty_abs 后 **0 行** | 🔴 **信号被清洗抹除** |

- 负数量问题根因：`qty_abs` 转换（P 能力测试已注明"负数量转正"）把"发货差错/退款"病症**修掉了**——清洗的职责是规范化，但企业优化恰恰需要负数量作为信号。设计上应保留"原始值 + 清洗值"双轨（或输出 `qty_abs_mapping` 类对照产物）。

## 三、问题分级与建议

| # | 问题 | 严重度 | 建议（v2.2 方向） |
|---|---|---|---|
| A2 | 合并后事实表外键 100% 失配 | 🔴 Critical | 引入**键映射表作为一等产物**（已有 `*-mapping.csv`，需升级为"全量映射"：每个被改键值 → canonical 键，供下游 join 时改写引用）；或声明"合并产物=左表视图增强，非主数据全集"，并在 schema 元数据标注 |
| A1 | 合并产物主键重复 | 🔴 Critical | `applyMerge` 改为**合并行语义**（右表独有列并入左表匹配行，而非追加新行）；追加行为仅当右表行在左表无匹配时发生（需加唯一性检查） |
| A3 | 同一实体分裂进两个实体 | 🟠 Important | validate 增加"同一 right.value 只允许一个 merge 声明引用"检查（P 规则）；生成器修正 SC-1..4 的重复引用 |
| B6 | 负数量信号被清洗抹除 | 🟠 Important | 转换规则增加"信号保留"约定：`qty_abs` 类规则输出 `-mapping`/`-original` 对照产物；engineering-principles 增加"清洗不得静默抹除业务信号"条款 |
| A4 | 消解覆盖率 8% | 🟡 Minor | demo 声明补足（194 对全声明）；文档明确"覆盖率"为可调参数 |

## 四、交付可用性判定

- **可用于**：数据质量修复后的单系统分析（转换产物 + 原表 join）；病症探查（5/6 类信号完整）。
- **不可直接用于**：跨系统客户主数据分析（合并产物关联破坏）、依赖负数量信号的流程优化（信号被抹）。
- **企业落地前提**：修复 A1-A3（引擎语义 + 声明校验）并落实"信号保留"约定（B6），否则合并产物交付出去会制造新的数据混乱——**"清洗过的混乱"比原始混乱更危险**（下游会信任它）。
