# 实验：merge-semantics

## 背景与动机
spec §3.1/§4 定义合并语义（v2 修正后的核心设计）：
- merge 是 **pair 级声明**（left/right 各一条记录）→ 执行 = 构建**键映射表**（右键 → 左键）→ 行级主键替换
- 产物: `output/<merge-id>.csv`（合并后表）+ `output/<merge-id>-mapping.csv`（主键映射表）
- 冲突策略（写死）: 左表（left.source）优先，右表仅补齐缺失字段
- fan-out 防护: join 前校验键唯一性，不唯一则中止
- 同名列冲突: 左侧优先，右列后缀 `_right`
- 合并仅限二元
- 合并作用于**实例数据行**
该语义是 v2 最大修正点（v1 概念错位：类型级 vs 实例级），且 merge-join-sqlite 实验只验证了 SQL JOIN 可行，**未验证**上述行级键映射语义。若键映射/冲突策略/唯一性防护实现不了或行为与 spec 不符，合并环节设计需要重做。

## 待验证假设
- H3a: 键映射替换正确——mapping 表 = 全部右键→左键对；合并后表主键替换为 canonical，右表缺失字段由左表补齐
  - H3a 推翻条件: 任一行的主键替换或字段补齐与 spec 预期不符
- H3b: 左表优先成立——左右表同名字段冲突时保留左值，右值进 `_right` 后缀列
  - H3b 推翻条件: 冲突列处理与预期不符
- H3c: fan-out 防护成立——left.source 或 right.source 主键不唯一时执行中止，无产物、状态不推进
  - H3c 推翻条件: 不唯一时仍产出或部分产出
- H3d: 合并作用于实例数据行（不是 objects.json 类型级 schema）
  - H3d 推翻条件: 实现需要类型级信息才能完成合并

## 变量
- 自变量: 左右表内容（重叠键/不重叠键/同名列/重复键注入）
- 因变量: 合并表行值、mapping 表内容、失败时产物状态
- 控制变量: Node 24.15.0、同一参考实现、同一 CSV 数据

## 方法
环境: Node 24.15.0 零依赖。
用例:
1. 正常合并: 左 4 行右 3 行（2 键重叠）→ 主键替换 + 补齐
2. 同名列冲突: 左右均有 `name` 列 → 左值保留，右值 `name_right`
3. fan-out: 右表主键重复 → 中止
4. 无重叠键: 右表键全不在左表 → 行为记录（spec 未定义，实验记录实际行为供 spec 补充）
运行: `node scripts/run.js`（输出 JSON：各用例 expected vs actual + 产物文件内容）。

## 成功标准（执行前定义）
- H3a/H3b/H3d 成立: 对应用例 actual === expected
- H3c 成立: fan-out 用例无产物文件、返回失败码
- 任一不满足 → 对应假设推翻；用例 4 为探索性（spec 语义缺口记录，不判成立/推翻）

## 偏差自检（设计时填写）
- 预设立场: 键映射替换是简单 dict 操作，冲突处理也好写；fan-out 检查容易
- 会打脸的结果: "右表仅补齐缺失字段"与"同名列 `_right` 后缀"并存时的字段语义冲突（例如右表有左表没有的列怎么办——spec 说补齐缺失字段，但"同名列加 _right"是否适用于"左表没有的列"？）；无重叠键时 mapping 表与合并表的行为未定义
- 可能遗漏的数据: 左右表列数不同、键列本身在同名列集合中、右表空

## 对设计的影响
- H3a-d 成立: §3.1/§4 合并语义确认可实现
- 任一推翻或发现语义缺口: 回写 spec 补充（无重叠键行为、右表独有列命名、键列冲突）
