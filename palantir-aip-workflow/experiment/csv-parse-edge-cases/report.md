# 实验报告：csv-parse-edge-cases

## 结论
H1a **成立**（现有解析器缺陷确证）、H1b **成立**（RFC 4180 状态机修复版全部通过，stringify 往返无损）。

## 结果数据
### H1a: 现有 parseCsv（schema-infer.js 抽取）
| 用例 | 预期 | 实际 | 判定 |
|---|---|---|---|
| BOM 前缀 | 表头 `id` | 表头 `\ufeffid`（BOM 污染） | ✗ 失败 |
| 转义引号 `"say ""hi"""` | `say "hi"` | `say hi`（丢引号） | ✗ 失败 |
| 引号内嵌换行 | 1 行 1 单元格含 `\n` | 切成 2 行 | ✗ 失败 |
| 空行保留 | 3 数据行（中间空行） | 2 行（空行被丢弃） | ✗ 失败 |
| 引用字段 `"z""q"` | `z"q` | `zq`（丢引号） | ✗ 失败 |
| CRLF 行尾 | 2 行 | 2 行 | ✓ 通过 |

### H1b: 修复版状态机解析
| 用例 | 判定 |
|---|---|
| 上述 6 用例 | 6/6 通过 |
| stringify 往返（parse→stringify→parse 值不变，2 组含逗号/引号/内嵌换行） | 2/2 通过 |

## 与假设对照
- H1a（现有实现有缺陷）：5/6 用例输出与预期不符 → **成立**
- H1b（修复方案可行）：6/6 用例 + 2/2 往返全部一致 → **成立**

## 对设计的影响
- spec §3.3 的"修复三缺陷 + 空行保留 + 新增 stringify"方案**确认可行**，可据此实现 `bin/csv.js`
- 修复版实现要点：单趟状态机（inQ 标志 + `""` 转义 + `\r\n` 处理 + BOM 剥离），复杂度约 30 行，零依赖
- 空行策略注意：修复版保留空行会得到 `['']` 单格行——exec 消费时需决定是否过滤（spec 说保留，写盘也保留，符合"不静默改数据"原则）

## 局限与后续
- 未测：非法引号（未闭合 `"`）、字段尾随空格、超大单元格（MB 级单格）——真实数据可能遇到，属防御性处理范畴
- 未测：BOM 在中间行出现（罕见）
