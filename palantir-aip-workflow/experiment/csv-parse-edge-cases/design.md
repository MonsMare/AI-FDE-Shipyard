# 实验：csv-parse-edge-cases

## 背景与动机
spec §3.3 断言：`bin/csv.js` 需从 `bin/schema-infer.js` 抽取解析器并**修复三缺陷**（BOM 剥离、转义引号 `"a""b"`、引号内嵌换行），空行策略改为**保留**，并新增 stringify（引号包裹、`""` 转义、行序稳定）。此断言尚未实测：
1. 现有 parseCsv 是否真的在这些用例上出错（缺陷存在性）；
2. RFC 4180 状态机式解析 + stringify 能否正确处理全部用例（修复可行性）。
若修复不可行或语义含糊，exec/validate 的数据底座就是错的，所有下游产物不可信。

## 待验证假设
- H1a: 现有 `schema-infer.js` 的 parseCsv 在 BOM、转义引号、引号内嵌换行、空行保留四个用例上产生错误输出。
  - H1a 推翻条件: 四个用例全部解析正确（则"修复"无对象，spec §3.3 需要改写）
- H1b: 按 RFC 4180 写的状态机 parseCsv（修复版）能正确处理全部边界用例，且 stringify(parse(x)) 往返一致。
  - H1b 推翻条件: 任一用例输出与 RFC 4180 预期不符，或往返不一致

## 变量
- 自变量: 解析实现（现有 parseCsv vs 修复版状态机）
- 因变量: 每用例解析出的 列数/行数/单元格值（与预期精确比对）
- 控制变量: 相同输入文本、相同 Node 版本（24.15.0）

## 方法
环境: Node 24.15.0，零依赖。
用例集（覆盖 spec 声称的缺陷 + 常规）:
1. BOM 前缀（`\ufeff` 在文件头）
2. 转义引号 `"a""b"` 单元格
3. 引号内嵌换行 `"line1\nline2"` 单元格
4. 空行保留（数据区中间空行）
5. 常规引用字段（逗号/引号混合）
6. stringify 往返: parse 后 stringify 再 parse，值不变；含引号/逗号/换行的值正确转义

运行: `node scripts/run.js`（输出 JSON 对照表，脚本只产数据）。

## 成功标准（执行前定义）
- H1a 成立: 现有 parseCsv 至少 1 个用例输出与预期不符
- H1a 推翻: 4 个用例全部正确
- H1b 成立: 修复版 6 个用例全部通过，往返一致
- H1b 推翻: 任一用例失败

## 偏差自检（设计时填写）
- 预设立场: 现有实现确实有缺陷（代码走查显示 BOM 未剥离、`""` 按翻转处理、split 切行）；修复版能通过
- 会打脸的结果: 现有实现对 `""` 的"翻转 inQ"恰好产生正确结果（例如 `"a""b"` 被解析为 `a"b`？——不对，RFC 4180 预期是 `a"b`，翻转逻辑可能碰巧正确）；修复版状态机引入新 bug
- 可能遗漏的数据: 引号包裹字段中的尾随空格、CRLF 行尾、字段内单个 `"`（非法但真实数据存在）

## 对设计的影响
- H1a+H1b 成立: spec §3.3 修复方案确认，可据此实现 bin/csv.js
- H1a 推翻: spec §3.3 的"修复三缺陷"改述为"重构抽取"
- H1b 推翻: 需调整解析策略（如换解析器方案），spec §3.3 重写
