# 实验：scale-benchmark

## 背景与动机
spec 背景（§1）指出当前实现的问题是"数据规模小（纯 Node 内存处理 CSV）"，架构决策（§2）选纯 JS 行级执行器，并记录"百万行是拍脑袋（合理性 D）"——即 spec **没有**承诺百万行规模。但用户愿景包含"规模大的环节外接数据库或自建服务（接口留好，后端可换）"，因此必须实测纯 JS 内存行级执行的真实资源边界，回答：
- 目标场景（万级行）是否无压力？
- 百万行级是否真的不可行（内存/耗时），还是可行？
- 资源边界数据应写进 spec 作为规模论证依据（替代"拍脑袋"）。

## 待验证假设
- H4a: 10 万行 CSV × 10 列 × 2 条规则（regex_replace + cast），纯 JS 行级执行 + 统一写盘，耗时 < 5s、峰值 RSS < 512MB
  - H4a 推翻条件: 耗时 ≥ 5s 或峰值 RSS ≥ 512MB 或进程崩溃
- H4b: 100 万行同场景，进程不崩溃（允许耗时长、内存高），记录真实数据
  - H4b 推翻条件: 进程崩溃/内存溢出被杀
- 探索性: 记录 10K/100K/1M 三档的耗时与峰值 RSS，供 spec 定规模上限与"外接 DB"触发线

## 变量
- 自变量: 行数（10K / 100K / 1M）
- 因变量: 总耗时（含解析/执行/写盘）、峰值 RSS、输出文件大小
- 控制变量: 同一生成器（固定种子生成可复现数据）、同一规则集、Node 24.15.0、同一实现

## 方法
环境: Node 24.15.0 零依赖。
- `scripts/gen.js N` 生成 N 行 CSV（固定种子，10 列，含脏数据可被 regex_replace/cast 处理）
- `scripts/run.js N` 读 CSV → 行级 2 规则 → 统一写盘 → 输出 {rows, elapsedMs, peakRssMB, outBytes}
- 峰值 RSS 用 `process.resourceUsage().maxRSS`（KB）换算
- 数据文件放 scripts/data/（生成后保留，可复现）；1M 行 ≈ 60-80MB 文本
运行: `node scripts/run.js 10000`、`node scripts/run.js 100000`、`node scripts/run.js 1000000`。

## 成功标准（执行前定义）
- H4a 成立: 100K 行 elapsedMs < 5000 且 peakRssMB < 512
- H4a 推翻: 100K 行 elapsedMs ≥ 5000 或 peakRssMB ≥ 512
- H4b 成立: 1M 行进程正常退出、产物完整
- H4b 推翻: 1M 行进程崩溃（OOM/被杀）

## 偏差自检（设计时填写）
- 预设立场: 10 万行纯 JS 应该 1-2 秒内完成、内存 < 200MB；100 万行可能 10-30 秒、500MB-1GB（可能接近内存边界）
- 会打脸的结果: 100K 行就超 5s（说明"行级 + 每次 RegExp"比想象慢）；1M 行反而很快（则"外接 DB"的紧迫性下降）
- 可能遗漏的数据: 峰值 RSS 是进程级（含 V8 堆外），不代表数据占用的纯增量；写盘时间占比（磁盘差异）；GC 抖动

## 对设计的影响
- H4a 成立: 万级/十万级目标场景确认纯 JS 可行，spec §2 规模论证从"拍脑袋"升级为实测数据
- H4a 推翻: 需重新评估行级执行方案（优化方向：预编译正则、批量写盘）或调整规模承诺
- H4b 数据: 为 spec 的"外接 DB 触发线"提供量化依据（如 ≥1M 行或 ≥512MB 建议换后端）
